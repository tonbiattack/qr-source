# 動画復元率の調査記録

2026-09-05に、スマートフォンでPCのQRスライドショーを撮影した動画を使って、`decode-video`の復元率を調査した記録です。個人環境の絶対パスや動画そのものはリポジトリに含めません。

## 結果

`--scan-fps 5`で解析した結果は次のとおりでした。

```text
Expected: 14 chunks
Found:    5 chunks
Frames scanned: 74
```

そのため、SHA-256検証・展開は行われず、復元は安全に中止されました。

## 観測条件

| 項目 | 観測値 |
| --- | --- |
| 動画 | HEVC、1920×1080、約14.79秒、約29.3MB |
| 元フレームレート | 約30fps |
| 解析レート | 5fps |
| 解析フレーム数 | 74 |
| スライド数 | 14 |
| 検出チャンク | 5 |

700ms間隔のスライドであれば、5fpsでも1枚あたり理論上3〜4フレームを解析できます。従って、この結果は単純なフレーム間引き不足だけでは説明できません。

動画から抽出したフレームには、`1 / 14`、`Resume`、`Enter fullscreen`が同時に表示されていました。これは、少なくともその時点ではスライドショーが停止中で、プレーヤー全画面も未実行だったことを示します。`First`は仕様上、先頭へ戻して一時停止します。したがって、`First`の後に`Resume`を押さずに撮影した場合、全スライドは動画に記録されません。

さらに、QRはモニター、操作UI、背景を含むフレーム内に撮影されており、高密度のセルが遠距離・斜め方向・HEVC圧縮の影響を受けています。固定領域への単純な切り出しも試しましたが、1fpsのサンプルでは読取率の有意な改善は確認できませんでした。単純なcropだけを恒久対策にはしません。

## 直ちに行う撮影対策

次の条件で再撮影します。

```bash
qr-source encode ./project
qr-source show ./qr-output
```

1. プレーヤーの`Enter fullscreen`を押す。
2. `First`を押した場合は、表示が`Resume`であることを確認してから押し、動作中の表示を`Pause`にする。
3. QR全体が大きく入る距離でカメラを固定する。
4. 14枚なら少なくとも2周分、約45秒を撮影する。

既定値は、動画撮影向けに500バイト、Q訂正、1080px、1500ms、コントローラー表示、無限ループへ更新しました。より低密度にしたい場合だけ`--chunk-size 300`を明示指定します。QRをさらに大きく表示したい場合だけ`--recording-mode`を使います。

## 実装上の優先対策

| 優先度 | 対策 | 狙い |
| --- | --- | --- |
| 1 | 実装済み: `show --recording-mode`でQRを最大化して操作UIを自動非表示にする | 撮影されるQRの面積を増やす |
| 2 | QR領域の検出、台形補正、正規化後の再読取 | 斜め撮影・画面外周・背景の影響を減らす |
| 3 | 同一QRの複数フレームから鮮明な候補を選び、必要に応じて時間方向にノイズ低減する | 動画の重複フレームを復元率へ活用する |
| 4 | 適応的なフレーム取得 | チャンク不足時だけ周辺フレームを高頻度で再解析する |

`--scan-fps`を一律に上げるだけでは、2メガピクセル級フレームに対するQR解析時間が増えます。まず撮影品質とQR密度を改善し、その後に領域検出・台形補正を実装して評価する方針です。

## 次の検証条件

改善の採否は、同一入力を使い、次の条件で比較します。

- QR数、チャンクサイズ、訂正レベル、表示間隔
- 全画面の有無、撮影距離、撮影周回数
- 検出チャンク数、全取得までのフレーム数、解析時間
- SHA-256検証と復元ファイルのハッシュ一致

全チャンク取得と復元ハッシュ一致を成功条件とします。
